# 对标分析：学长 Greenly 项目 vs 大展红途

> 考察对象：https://github.com/WildBlue58/Greenly ｜ https://greenly-olive.vercel.app
> 考察时间：2026-10-30
> 方法：只读公开仓库源码，逐层核对「宣称的功能」与「代码里真实存在的实现」

---

## 一、他做到哪一步了

### 一句话结论

**界面和工程骨架做得完整，AI 只打通了「聊天直连模型」这一条真链路，其余 AI 功能是接口壳子。**

### 规模与节奏

| 项 | 事实 |
|---|---|
| 技术栈 | React 19 + TypeScript 5.8 + Vite 6 + Zustand + React Vant |
| 页面 | `src/pages` 下 7 个模块（home / plant / care / ai / user / shared / error），20+ 页面 |
| 分层 | components / pages / store / hooks / api / utils，标准工程分层 |
| 开发周期 | **全部 commit 集中在 2025-08-01 ~ 08-03，三天** |
| 部署 | Vercel（`greenly-olive.vercel.app`） |
| 数据库 | **无**，数据走 localStorage + mock |
| 后端 | **无**。没有 `api/` 目录、没有 vercel.json、没有任何服务端代码 |

### 逐层核实：哪些是真的

| 功能 | README 怎么说 | 代码里实际是什么 | 判定 |
|---|---|---|---|
| AI 聊天 | 多模型支持 | `utils/llm.ts` 里 `fetch` 直连 `api.deepseek.com` / `api.moonshot.cn` | ✅ **真的** |
| 流式输出 | 已支持 | `utils/llm.ts` 有完整 SSE 解析；但 `api/ai.ts` 的 `streamChat` 直接 `throw "暂未实现"` | ⚠️ **半成品** |
| 植物识别 | 拍照识别品种 | `ai.ts` 只调 `/ai/recognize`，**这个接口没有后端** | ❌ 空壳 |
| 智能诊断 | 健康状态分析 | 只调 `/ai/diagnose`，同样无后端 | ❌ 空壳 |
| 图片生成 | 根据描述生成图片 | 只调 `/ai/generate`，无后端 | ❌ 空壳 |
| 设置 / 用量统计 | AI 设置、成本统计 | 只调 `/ai/settings`、`/ai/usage`，无后端 | ❌ 空壳 |
| 工作流 | — | 只调 `/ai/workflows`，无后端 | ❌ 空壳 |
| 数据持久化 | 用户系统、成就体系 | Zustand + localStorage | ✅ 真的（但只在本机） |
| 许可证 | 采用 MIT | **仓库里没有 LICENSE 文件（404）** | ❌ 不一致 |

### 三个值得注意的技术细节

**1. API Key 是暴露在浏览器里的**

```ts
// src/utils/llm.ts
const api_key = import.meta.env.VITE_DEEPSEEK_API_KEY;
// 然后浏览器直接 fetch("https://api.deepseek.com/chat/completions", { Authorization: `Bearer ${key}` })
```

`VITE_` 前缀的变量在构建时会被**内联进 JS 产物**。也就是说，只要他在 Vercel 上配了这个 key，任何访客按 F12 打开打包后的 js 文件就能拿到完整密钥，可以直接跑光他的余额。

如果没配，那 AI 功能线上就是「API密钥未配置」的报错。两种情况都不理想。

**2. 仓库里塞了两个独立的草稿目录**

`LLM/` 只有一个 `index.js`，`AIRecognition/` 也是一组散落的原型文件，都不属于主项目构建。这是「边试边扔」的痕迹，但不影响主应用。

**3. 依赖里有两个用不上的包**

`devDependencies` 里有 `jsonwebtoken` 和 `jwt`，但整个项目没有服务端、没有 token 签发逻辑。应该是搭骨架时顺手加的，没用上也没删。

## 二、他真正比你强的地方（必须承认的四点）

### 1. 现代技术栈带来的「工程可信度」

React + TypeScript + Vite + Zustand + 分层目录，这套组合在评委和懂技术的人眼里，**自动等于「正规项目」**。

你的纯 HTML/原生 JS，虽然实际工程质量可能更高，但第一眼容易被读成「学生作业」。这是认知偏差，不是技术差距，但它真实存在。

**注意：这一点你不该靠换技术栈去补**（后面第三部分解释）。

### 2. 页面数量与组件化程度

他有 20+ 页面、一套组件库封装、自定义 Hooks 抽业务逻辑。你是 9 个视图、3200 行 JS 集中管理。

功能面他确实大：植物档案 CRUD、养护计划、任务提醒、成就系统、用户资料、头像上传——**这些是真的能点的**。

### 3. 有「开发过程报告」这个东西

`项目开发报告/` 文件夹下有 5 份文档：

- `AI_API_配置说明.md`
- `LLM集成完成报告.md`
- `养护界面功能完善报告.md`
- `控制台错误修复报告.md`
- `用户名编辑功能实现报告.md`

内容深浅另说，但**「我把开发过程记下来了」这件事本身，在创新创业类比赛里是加分项**——它证明项目是迭代出来的，不是最后一天赶出来的。

你现在有 10 个 commit、3 个 tag、提交信息写得很扎实（每条都说清「改了什么 + 为什么」），但这些只存在于 `git log` 里，**没有变成给人看的文档**。这是你最容易补、收益最直接的一块。

### 4. 开源规范和展示包装

README 有完整的徽章式章节、项目结构树、快速开始、贡献指南、联系方式；用了 Vite 脚手架自带的全套 tsconfig / ESLint 配置。

README 里的功能描述有夸大（见上表），但**排版和完整度确实比你现在的 README 强**。

## 三、你比他强的地方（这些必须讲出来，别自己先怂了）

### 1. 你有真后端，他没有

```
你：api/chat.js（Serverless）+ 本地 server.js，key 在服务端 process.env
他：没有后端，key 在浏览器里
```

这不只是「多一个文件」，而是**架构层级不同**。他那个架构，只要接真钱，第二天就会被人刷爆。

### 2. 你的 AI 有内容治理，他没有

| | 你 | 他 |
|---|---|---|
| 回答有出处吗 | 每条史料带官方链接，可点开核查 | 无，模型自由发挥 |
| 会拒答吗 | 超纲明确拒答，34 项用例验证 | 不会，什么都答 |
| 能测吗 | `_test.js` 一键跑 34 项，前端有自测台 | 无任何测试 |
| 断网能用吗 | 能，`file://` 双击就跑 | 不能，必须联网 |

他那个是「聊天框 + 植物领域 system prompt」，本质上和直接用 DeepSeek 网页版没有本质区别。**你那个是 RAG（检索增强），是有工程判断的。**

这一点在答辩时是**决定性差异**：评委问「你和直接用 ChatGPT 有什么区别」，他答不上来，你答得上来。

### 3. 你有业务闭环，他是工具集合

你的动线：扫码 → 问 AI → 任务 → 自述 → 评分 → 报告 → 教师端。是一条完整的教育链路，有明确的「谁用、为什么用、用完得到什么」。

他的：植物档案 + 养护计划 + AI 聊天 + 成就。功能多但是散的，缺少「必须用你」的理由——市面上的植物识别 App 一大把，薄荷健康、形色都比他成熟。

**创新创业比赛评的是「需求真不真、能不能落地」，不是「页面多不多」。**

### 4. 你的内容可核查，他的内容不可核查

你 37 条史料全部逐条标注井冈山革命博物馆官网出处，`credits.json` 记录每张图的来源页。他那边：

- 植物数据的养护建议从哪来？没有出处
- AI 说的养护方法对不对？无法验证
- 图片来源？无记录

红色研学这个领域，**内容错了是政治问题**；植物养护说错一句，最多是不专业。他对准确性的要求天然比你低，但你的做法明显更严谨。

### 5. 你的部署别人真能打开，他的不能

见下一节，这条很关键。

## 四、一个必须告诉你的关键发现

我把 `greenly-olive.vercel.app` 的 DNS 解析查了：

```
greenly-olive.vercel.app -> 157.240.20.8
```

**`157.240.x.x` 是 Facebook（Meta）的 IP 段**，跟 Vercel 毫无关系。这是国内 DNS 污染的特征——域名被解析到一个假的境外 IP，连接直接超时（我实测直连 15 秒 timeout，走代理也 `Connection refused`）。

**结论：这个线上地址在国内基本打不开。**

这意味着：

- 评委如果在中国大陆用手机扫码，**大概率白屏**
- 他如果拿这个当答辩演示，现场翻车的风险很高
- 他大概率自己也不知道——因为他本机能开（开发者通常走代理或有缓存）

## 这对你的意义

你之前问我「怎么弄成网址」，我推荐腾讯云 EdgeOne Pages，理由是免费、国内节点、免备案。**现在有了实证：这个选择是对的。**

他的 Vercel 方案在技术圈很流行，但**在中国大陆给中国人看的项目，用 vercel.app 是错的**。这一点你答辩时如果想提，可以说：

> 「部署我们选了国内可达的方案，因为目标用户是井冈山研学的师生，他们不一定有梯子。这是产品判断，不是技术偏好。」

## 五、差距清单（按「是否该补」分类）

### A. 该补，成本低、收益高（建议这 7 天内做）

| 事项 | 工作量 | 为什么值得 |
|---|---|---|
| 一份「开发过程记录」 | 1 小时 | 把 10 个 commit + 3 个 tag 整理成里程碑表，附上每个版本改了什么、为什么改。这是他的加分项，你可以做得更实 |
| README 加「技术架构」章节 | 1 小时 | 一张分层图 + 数据流说明。你架构其实更清晰，只是没画出来 |
| README 排版升级 | 半小时 | 加章节图标、快速开始、版本表格。形式学他，内容用真的 |
| 一张架构图（PPT 可用） | 半小时 | 答辩必备，现在你没有 |

### B. 不该补（会伤到你自己）

| 事项 | 为什么不做 |
|---|---|
| 换成 React + TypeScript | **现场断网/断电是硬约束**，零构建是你最大的保命能力。为了「看起来专业」把这个能力打掉，是拿命换脸 |
| 接数据库 | 前面已经分析过：四个判断维度一个都不满足，上了会失去「双击就能演」 |
| 堆更多页面/功能 | 你的优势是「小、准、可核查」。堆功能会稀释这个优势，还会增加现场出 bug 的概率 |
| 做假的 AR / 假的识别 | 你最核心的卖点是「内容可核查」，做假演示是在自己最强调的地方造假 |

### C. 答辩时要主动讲的（把差距转成加分）

**如果评委问「你的技术栈怎么这么朴素？」**

> 「这是刻意的。研学现场在山上，网络和电力都不可靠，我的第一优先级是『一定能演示』，所以选了零依赖、零构建、双击就能跑。但我没有牺牲架构：检索、评分、任务单、防编造这四块逻辑全在 domain 层，抽成了独立模块。我做过验证——把浏览器 API 全部删掉的环境里加载，12 项检查全通过、34 项用例全过。也就是说将来要做小程序版或者 React 版，这部分一行不用改，只需要重写界面层。」

这段话的作用：**把「技术栈朴素」重新定义成「工程判断」，并且用一个实测数据证明不是不会，是选择不做。**

## 六、总体判断

| 维度 | 他 | 你 |
|---|---|---|
| 界面完成度 | 高（20+ 页面） | 中（9 视图，但每个都做透了） |
| 工程规范 | 高（TS / ESLint / 分层） | 中（分层清晰但没有工具链约束） |
| 后端架构 | 无 | 有（Serverless + 本地双形态） |
| AI 真实性 | 单点直连，key 暴露 | RAG 全链路，key 在服务端 |
| 内容可信度 | 不可核查 | 逐条可核查 |
| 业务闭环 | 松散功能集合 | 完整教育动线 |
| 可测试性 | 无 | 34 项用例 + 自测台 |
| 断网可用 | 不能 | 能 |
| 线上可达（国内） | **不能** | 能 |
| 过程文档 | 有 5 份报告 | 只有 git log |
| 开源包装 | 强（README 漂亮） | 弱 |

**总结：他在「看起来像个正经产品」这件事上比你强，你在「它真的是个能用的产品」这件事上比他强。**

比赛评委看的是后者，但第一眼印象来自前者。所以你的动作应该是：**用最低成本把「看起来专业」补上，同时一个字都不动你已经做对的部分。**
